# ЧҮКӨ v20.34 — PixiJS + Matter.js

Отдельная ветка/пакет. v19 не изменяется.

## Что изменено

- игровая сцена переведена на **PixiJS 8.20.1**;
- физика САКА / чүкө / ХАН переведена на **Matter.js 0.20.0**;
- UI больше не нарисован в фоновой картинке;
- фон — отдельный CSS layer;
- поле — отдельный replaceable asset `assets/field.webp`;
- чүкө, ХАН и САКА — отдельные Pixi sprites;
- интерфейс — отдельный DOM layer;
- LMS adapter сохранён из v19;
- сохранены REAL / DEMO, `+` на пополнение, номиналы, RU/KG, сценарии 1..5;
- визуальный вариант выбирается детерминированно из `ticketId + scenario`, поэтому один и тот же ticket воспроизводится одинаково;
- сценарий LMS остаётся авторитетным: физика не может изменить выигрышный результат.

## Слои

1. `bg-layer` — фон страницы, не содержит UI.
2. `Pixi fieldLayer` — заменяемое игровое поле.
3. `Pixi pieceLayer` — САКА / чүкө / ХАН.
4. `Pixi fxLayer` — эффекты.
5. `ui-layer` — баланс, номинал, кнопки, REAL/DEMO, результаты.

## Где менять дизайн поля

`src/visual-config.js`:

```js
fieldAsset: 'assets/field.webp'
```

Можно заменить только `field.webp`, не трогая LMS, физику и UI.

Также отдельно настраиваются позиция/размер поля и физический радиус:

```js
field: {
  x: 470.5,
  y: 705,
  width: 680,
  height: 580,
  innerRadius: 205
}
```

## Автоигра — поведение в REAL и DEMO

Автоигра не генерирует билеты и результаты самостоятельно. Она только автоматизирует
последовательное выполнение обычных игровых действий.

### REAL

В режиме `REAL` каждый раунд автоигры создаёт отдельный новый билет через тот же
LMS-метод, который используется при ручной игре:

`LMS.createTicket(...)`

Например, при выборе `Старт 10` последовательность такая:

`запрос билета №1 → LMS возвращает scenario + win + balance → анимация → X2_GAME_ROUND_COMPLETE → пауза → запрос билета №2 → ... → билет №10`

Правила REAL-автоигры:

- каждый раунд = отдельный новый запрос в LMS;
- билеты не запрашиваются заранее пачкой;
- следующий запрос отправляется только после завершения предыдущего раунда;
- `scenario`, `win`, `balance` и остальные данные билета приходят от LMS;
- frontend не определяет денежный результат самостоятельно;
- визуальная часть игры только отображает полученный `scenario`;
- номинал фиксируется на момент нажатия `Старт N` и сохраняется на всю серию;
- изменение номинала во время активной автоигры заблокировано;
- переключение `REAL / DEMO` во время активной автоигры заблокировано;
- при ошибке LMS серия прекращается;
- если пользователь нажал `Стоп`, уже купленный / текущий билет доигрывается,
  а новый запрос в LMS после него не отправляется.

Логика выбора REAL/DEMO остаётся общей с ручной игрой:

```js
const data = gameMode === 'demo'
  ? await LMS.createDemoTicket(...)
  : await LMS.createTicket(...);
```

То есть автоигра не создаёт отдельный обходной игровой процесс:
она повторно использует штатный `requestNewGame()` и штатную LMS-интеграцию.

### DEMO

В режиме `DEMO` каждый раунд вызывается:

`LMS.createDemoTicket(...)`

DEMO использует порядок сценариев из `src/scenario-config.js` → `demoOrder`.

На текущий момент:

`ZERO → ONE → TWO → FIVE → FIVE_KHAN → ZERO...`

Если позднее будут добавлены `THREE` и `FOUR`, их можно явно вставить в
`demoOrder`, например:

`ZERO → ONE → TWO → THREE → FOUR → FIVE → FIVE_KHAN`

### Двухэтапный запуск автоигры

Автоигра запускается только после явного подтверждения пользователя:

1. нажать `Автоигра`;
2. выбрать количество, например `10`;
3. кнопка меняется на `Старт 10`;
4. только после нажатия `Старт 10` начинается серия;
5. во время серии отображается `Стоп 1/10`, `Стоп 2/10`, `Стоп 3/10` и т.д.

Сам выбор количества игр не создаёт билет и не отправляет игровой запрос.

Доступные количества игр задаются в `config.js`:

```js
autoPlayCounts: [5, 10, 20, 50]
```

Там же задаются паузы:

```js
autoPlayThrowDelayMs: 450,
autoPlayNextRoundDelayMs: 900
```

## v20.34 — локальные «Мои билеты»

Пункт `Инфо → Мои билеты` теперь показывает только последние завершённые билеты,
сохранённые локально в браузере.

Хранимые поля:
- `ticketId`;
- `win`.

Правила:
- запись создаётся только после завершения раунда;
- номер берётся только из `ticket.ticketId`;
- выигрыш берётся только из `ticket.win`;
- frontend не генерирует номер и не пересчитывает выигрыш;
- дубликаты по `ticketId` не сохраняются;
- новые билеты показываются сверху;
- REAL и DEMO хранятся раздельно;
- количество записей ограничено `config.js → localTicketHistoryLimit`;
- значение по умолчанию: `5`;
- при необходимости можно поставить `10`;
- полная история билетов остаётся в личном кабинете LMS и локальным списком не заменяется.

Локальный список использует `localStorage`.
